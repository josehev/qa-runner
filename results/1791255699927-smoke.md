## 1. ACCESSIBILITY (WCAG 2.1/2.0 AA)

| Check | Result |
|---|---|
| Keyboard reachability of interactive elements | **PASS** — Tabbed through header, FAQ, cards, and footer links; all were reachable in DOM order. |
| Visible focus indicator | **FAIL** — The 5 FAQ accordion `<button>` elements (e.g. "Q: Do I need to own the appliance?") have `outline-style: none`, `outline-width: 0px`, and `box-shadow: none` when focused via keyboard — no visible focus ring at all. Most other links (nav, footer, "BACK TO TOP") do show a visible `outline: solid 2px`. **Repro:** Load page → press Tab until focus reaches an FAQ question button → observe no visible focus styling (confirmed via computed style inspection, not just visual). |
| Logical tab order / no keyboard traps | **PASS** — Tab order followed visual/DOM order; no trap encountered during a 15-element tab sweep. |
| Skip-to-content link | **PASS** — First focusable element is "Skip to Main Content" (`href="#mainContent"`); activating it moves focus to the `#mainContent` element. |
| Alt text on images | **PASS** — All 10 `<img>` elements on the rendered page have non-empty, descriptive `alt` attributes (e.g. "An illustration of a customer using a laptop representing appliance eligibility."). 0 images missing `alt`. |
| ARIA landmarks (header/nav/main/footer) | **FAIL** — `<header>`(1), `<nav>`(2), `<footer>`(1) are present, but there is **no `<main>` element and no `role="main"`** anywhere on the page. The "main content" wrapper is a plain `<div id="mainContent">` with no semantic/ARIA role. Screen reader users have no way to jump to main content via landmark navigation. |
| Heading hierarchy | **FAIL** — Hidden/off-canvas modal markup injects headings before the visible H1: order detected was `H4(empty text) → H3("Verify Your Identity") → H5("To protect your account...") → H1("Get Rewarded for Recycling")`. | Icon-only buttons have accessible names | **PASS** — Spot-checked login/search/menu-toggle buttons; all carry `aria-label` ("login", "search", "toggle menu"). |
| Form field labels | **PARTIAL / FAIL** — The visible header search input (`#searchId`) has no `<label>`, relying only on `aria-label="search"` and a placeholder "SEARCH" (acceptable per WCAG as aria-label counts, so this one is fine). However, the hidden login-modal email/password fields do have associated `<label for>` elements (PASS), but a hidden MFA input is present with `required=true` and no visible label text evaluated beyond `for` association — could not fully exercise this flow without real credentials (see note below). |
| Form error messaging | **NOT TESTED** — No submittable form could be exercised to failure without live credentials/backend state (login requires real account, search submits to a results page not rendered in this audit). |
| Color contrast (body text, buttons, FAQ, footer, nav) | **PASS** — Measured actual computed `color`/`background-color` pairs and calculated contrast ratios: H1/body text #2A2A2A on white = 14.35:1; CTA button white-on-teal (#004557) = 10.56:1; footer links on light gray = 11.50:1; FAQ question text = 14.35:1; orange anchor-nav tabs (teal #004557 text on #FF8E2C orange) = 4.60:1 (passes the 4.5:1 minimum, but only barely — worth monitoring if colors are adjusted). All sampled combinations meet or exceed WCAG AA. |
